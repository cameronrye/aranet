This guide covers running aranet-service as a persistent background service. The `aranet` CLI from the [downloads](/aranet/docs/downloads/) runs the same service as `aranet server`. The standalone `aranet-service` binary, which can also install itself as a service, comes from `cargo install aranet-service --features full`.

## Deployment Options

| Platform | Service Manager | Installed as |
|----------|----------------|--------------|
| macOS | launchd (per-user LaunchAgent) | `~/Library/LaunchAgents/dev.rye.aranet.plist` |
| Linux | systemd (system service) | `/etc/systemd/system/aranet.service` |
| Linux | systemd (user service) | `~/.config/systemd/user/aranet.service` |
| Docker | Docker Compose | `docker-compose.yml` or `docker/docker-compose.yml` |
| Windows | Task Scheduler | A task that starts the service at logon |

`sudo aranet-service service install` installs a system-level service only on Linux with systemd, where the service runs as an unprivileged user. On macOS, Windows, OpenRC and rc.d it refuses, because the service would run as root there. Use `aranet-service service install --user` on macOS, Task Scheduler on Windows (see [Windows](#windows)), and an init script of your own that runs `aranet-service run` as an unprivileged user on OpenRC and rc.d.

## macOS (launchd)

On macOS the service runs as a LaunchAgent: as you, while you're logged in, with your own config and database.

<Steps>
1. Install aranet-service
   ```bash
   cargo install aranet-service --features full
   ```

2. Install the LaunchAgent
   ```bash
   aranet-service service install --user
   ```

3. Start the service
   ```bash
   aranet-service service start --user
   ```

4. Check status
   ```bash
   aranet-service service status --user
   ```
</Steps>

The agent reads `~/Library/Application Support/aranet/server.toml`. To use another file, name it when you install: `aranet-service service install --user --config /path/to/server.toml`. If polls fail because Bluetooth access is denied, allow `aranet-service` under **System Settings → Privacy & Security → Bluetooth**. Remove the agent with `aranet-service service uninstall --user`.

A system-level install (`sudo aranet-service service install`) is refused on macOS, because launchd would run the service as root.

### Manual Configuration

The agent that `service install --user` writes doesn't keep a log. For a log file, write the agent yourself instead, and don't also run `service install --user`, which uses the same label. Create `~/Library/LaunchAgents/dev.rye.aranet.plist`, replacing `/Users/you` with your home directory (launchd doesn't expand `~`):

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
    <key>Label</key>
    <string>dev.rye.aranet</string>
    <key>ProgramArguments</key>
    <array>
        <string>/Users/you/.cargo/bin/aranet-service</string>
        <string>run</string>
    </array>
    <key>RunAtLoad</key>
    <true/>
    <key>KeepAlive</key>
    <true/>
    <key>StandardOutPath</key>
    <string>/Users/you/Library/Logs/aranet-service.log</string>
    <key>StandardErrorPath</key>
    <string>/Users/you/Library/Logs/aranet-service.log</string>
</dict>
</plist>
```

Load it, and unload it when you no longer want it:

```bash
launchctl bootstrap "gui/$(id -u)" ~/Library/LaunchAgents/dev.rye.aranet.plist
launchctl bootout "gui/$(id -u)/dev.rye.aranet"
```

## Linux (systemd)

### System Service

The system service is `aranet.service`. It runs aranet-service as a dynamic, unprivileged `aranet` user with no extra capabilities, reads `/var/lib/aranet/server.toml` and keeps its database in `/var/lib/aranet`. You don't create the user or the directory: systemd does when the service starts. (With a dynamic user, systemd keeps the directory at `/var/lib/private/aranet` and links `/var/lib/aranet` to it; as root, either path works.)

<Steps>
1. Install aranet-service where only root can change it
   ```bash
   cargo install aranet-service --features full
   sudo install -o root -g root -m 0755 ~/.cargo/bin/aranet-service /usr/local/bin/aranet-service
   ```
   The installer refuses a program that a non-root user could replace, such as `~/.cargo/bin/aranet-service` itself or a build in `target/`.

2. Install and start the service
   ```bash
   sudo /usr/local/bin/aranet-service service install
   sudo systemctl start aranet
   ```
   Or install the unit from the repository yourself: `sudo install -m 0644 distribution/systemd/aranet.service /etc/systemd/system/aranet.service`, then `sudo systemctl daemon-reload` and `sudo systemctl enable --now aranet`.

3. Add your sensors, then restart
   ```bash
   sudoedit /var/lib/aranet/server.toml
   sudo systemctl restart aranet
   ```

4. Check status and logs
   ```bash
   systemctl status aranet
   journalctl -u aranet -f
   ```
</Steps>

`service install --config <file>` makes the unit read another config file. A path that contains `..`, or that lies in `/home`, `/root`, `/run/user`, `/tmp` or `/var/tmp` (also when a symlink leads there), is refused at install time, because the unit hides those directories from the service.

If the journal shows that BlueZ refused access (`org.freedesktop.DBus.Error.AccessDenied`), let the service use the `bluetooth` group with a drop-in:

```bash
sudo mkdir -p /etc/systemd/system/aranet.service.d
printf '[Service]\nSupplementaryGroups=bluetooth\n' | sudo tee /etc/systemd/system/aranet.service.d/bluetooth.conf
sudo systemctl daemon-reload
sudo systemctl restart aranet
```

To remove the service, stop it first: `sudo aranet-service service stop`, then `sudo aranet-service service uninstall`.

The system service has no desktop session, so desktop notifications (the `notifications` feature) don't reach anyone from it: use webhooks or MQTT there, or a [user service](#user-service).

#### Running the released `aranet` binary

The release downloads contain `aranet`, not `aranet-service`, and `aranet server` runs the same service. To run it under this unit, copy it where only root can change it, install the unit, and replace the unit's command with a drop-in:

```bash
sudo install -o root -g root -m 0755 ~/.cargo/bin/aranet /usr/local/bin/aranet
sudo install -m 0644 distribution/systemd/aranet.service /etc/systemd/system/aranet.service
sudo mkdir -p /etc/systemd/system/aranet.service.d
printf '[Service]\nExecStart=\nExecStart=/usr/local/bin/aranet server --config /var/lib/aranet/server.toml\nEnvironment=RUST_LOG=aranet_service=info\n' \
  | sudo tee /etc/systemd/system/aranet.service.d/aranet-cli.conf
sudo systemctl daemon-reload
sudo systemctl enable --now aranet
```

#### Upgrading from a 0.2.x system service

Earlier versions installed the system service as `rye-aranet.service`, running as root. Every `aranet-service service` command warns while that unit is still installed; `sudo aranet-service service install` stops and removes it (or `sudo aranet-service service uninstall` removes it without installing the new one). Its config and database stay where they were, by default `/root/.config/aranet/server.toml` and `/root/.local/share/aranet/data.db`. To keep them, copy them into `/var/lib/aranet` after the first start of `aranet.service`, and give them to the service's user. `sudo aranet-service service install` prints these steps when it finds the old config:

```bash
sudo systemctl start aranet && sudo systemctl stop aranet    # creates /var/lib/aranet
sudo cp /root/.config/aranet/server.toml /var/lib/aranet/
sudo sh -c 'rm -f /var/lib/aranet/data.db*'
sudo sh -c 'cp /root/.local/share/aranet/data.db* /var/lib/aranet/'
sudo chown -R --reference=/var/lib/aranet /var/lib/aranet/
sudoedit /var/lib/aranet/server.toml    # if storage.path points under /root, delete that line
sudo systemctl start aranet
```

The `rm` removes the empty database that the first start created, with its `-wal` and `-shm` files, so none of them is applied to the old database. The `cp` copies the old database together with its own `-wal` and `-shm` files, if any, so no reading that is still only in the write-ahead log is lost. The globs run in `sh -c` because your own shell can't list `/root` or `/var/lib/aranet`. Without a `storage.path`, the service uses the database in `/var/lib/aranet`.

### User Service

A user service runs as you, with `~/.config/aranet/server.toml` and your own database, and needs no root:

```bash
aranet-service service install --user
aranet-service service start --user
aranet-service service status --user
journalctl --user -u aranet -f
```

It runs while you're logged in; `loginctl enable-linger "$USER"` keeps it running after you log out. A user service that 0.2.x installed as `rye-aranet.service` is stopped and removed when you install the new one.

## Windows

`aranet-service service install` doesn't support Windows yet: the program can't run as a Windows service. Start the service at logon with Task Scheduler instead. Creating a logon task needs a Command Prompt opened with **Run as administrator**; `/ru` and `/it` keep the task running as you, in your session. For the `aranet` CLI from the installer:

```text
schtasks /create /tn "Aranet Service" /tr "\"%USERPROFILE%\.cargo\bin\aranet.exe\" server" /sc onlogon /ru "%USERNAME%" /it
```

With `aranet-service` from `cargo install`, use `"\"%USERPROFILE%\.cargo\bin\aranet-service.exe\" run"` as the `/tr` value instead. The task runs as you, with `%APPDATA%\aranet\server.toml` and your own database, in a console window that stays open while the service runs. Remove it with `schtasks /delete /tn "Aranet Service"`, also from an administrator prompt. Without administrator rights, put a shortcut to `aranet.exe server` (or `aranet-service.exe run`) in your Startup folder (Win+R, `shell:startup`) instead.

## Docker

`docker/Dockerfile` builds an image that runs aranet-service as an unprivileged user (uid and gid 999) and always reads `/app/server.toml`. The image holds a copy of [`docker/server.toml`](https://github.com/cameronrye/aranet/blob/main/docker/server.toml), and both compose files mount that file over it. A config that fails validation stops the container; `docker logs aranet-service` shows why.

### Quick Start

```bash
# Standalone service, from the repository root
docker compose up -d

# Dashboard: http://127.0.0.1:8080/dashboard
```

The compose files publish their ports on `127.0.0.1` only, so the dashboard and API (and Prometheus and Grafana in the monitoring stack) are reachable from this machine but not from the network.

### Full Monitoring Stack

Use the `docker/` directory for a Prometheus + Grafana stack:

```bash
docker compose -f docker/docker-compose.yml up -d
```

For Bluetooth, uncomment the `/run/dbus:/run/dbus:ro` volume of `aranet-service` in `docker/docker-compose.yml`. Grafana is at http://127.0.0.1:3000 (user `admin`, password `changeme` unless you set `GRAFANA_ADMIN_PASSWORD`).

### Editing the Configuration

Edit `docker/server.toml` and restart the container (`docker compose restart aranet-service`). The compose files mount it read-only, so adding, changing or removing a sensor through the API, the TUI or the GUI fails with `500 Internal Server Error`. To manage sensors that way, mount a writable copy that uid 999 can write, without `:ro`:

```bash
cp docker/server.toml server.toml
sudo chown 999:999 server.toml
# in the compose file: - ./server.toml:/app/server.toml
```

The service then rewrites that file in place, keeping its comments. It can't replace a single mounted file, so an interrupted write can leave it incomplete: keep a copy.

### Bluetooth in Docker

Bluetooth works on a Linux host running BlueZ: mount the host's `/run/dbus` read-only (`/run/dbus:/run/dbus:ro`), and the service talks to BlueZ over the system bus. No privileged mode, host networking or device nodes are needed. Docker Desktop on macOS and Windows can't reach the host's Bluetooth adapter; run the service natively there.

If the log shows `AccessDenied` for `org.bluez` or the system bus:

- BlueZ may accept only members of the host's `bluetooth` group. Add its group id (`getent group bluetooth`) to the service with `group_add: ["<gid>"]`.
- AppArmor (Ubuntu) or SELinux (Fedora, RHEL) may block the container's D-Bus messages. Lifting that confinement for this one container is the way out; the root `docker-compose.yml` has both lines, commented out:

  ```yaml
      security_opt: ["apparmor=unconfined"]  # Ubuntu and other AppArmor hosts
      # security_opt: ["label=disable"]      # SELinux hosts (Fedora, RHEL)
  ```

### Build from Source

```bash
docker build -f docker/Dockerfile -t aranet-service .
docker run -d --name aranet-service \
  -p 127.0.0.1:8080:8080 \
  -v /run/dbus:/run/dbus:ro \
  -v aranet-data:/data \
  -v "$PWD/server.toml:/app/server.toml:ro" \
  aranet-service
```

Build from the repository root with `-f docker/Dockerfile`; there is no `Dockerfile` at the root any more. The Dockerfile needs BuildKit (it uses cache mounts and `COPY --chmod`), the default builder since Docker 23 when the buildx plugin is installed (on Debian and Raspberry Pi OS, the `docker-buildx` package). An older engine may build it with `DOCKER_BUILDKIT=1 docker build …`; if that fails on `--chmod`, update Docker. `docker compose` needs the Compose v2 plugin. The mounted `server.toml` must be readable by uid 999 (`chmod 644 server.toml`, or `sudo chown 999:999 server.toml` if it holds secrets). Arguments after the image name replace the default `run` command and still read `/app/server.toml`, for example `docker run … aranet-service run --no-collector`.

### Production Deployment

```yaml
# docker-compose.prod.yml, in the repository root
services:
  aranet-service:
    build:
      context: .
      dockerfile: docker/Dockerfile
    restart: always
    ports:
      - "127.0.0.1:8080:8080"
    volumes:
      - aranet-data:/data
      - ./server.toml:/app/server.toml:ro
      - /run/dbus:/run/dbus:ro
    environment:
      - RUST_LOG=aranet_service=info

volumes:
  aranet-data:
```

The image has its own health check on `/api/health`.

<Aside type="caution">
  Inside the container the service must listen on `0.0.0.0`, a network address, which it refuses without API-key authentication. `docker/server.toml` therefore sets `security.allow_unauthenticated_network = true`: the compose files publish the port on `127.0.0.1` only, and Prometheus reaches the service over the compose network. It also lists `aranet-service`, the name Prometheus uses, in `security.allowed_hosts`. Keep both settings in your own `server.toml`, or turn on API-key authentication, which you must do before publishing the port on any other address. With authentication on, give Prometheus the key with an `authorization` block (see [Prometheus Integration](#prometheus-integration)), and set `api_key` yourself: the service can't save a generated key to a read-only file.
</Aside>

## Configuration

### Server Configuration

The service reads `server.toml` from `~/.config/aranet/` on Linux, `~/Library/Application Support/aranet/` on macOS and `%APPDATA%\aranet\` on Windows, or the file you pass with `--config`. The systemd system service uses `/var/lib/aranet/server.toml`, and the Docker image `/app/server.toml`.

```toml
[server]
bind = "127.0.0.1:8080"

[storage]
path = "~/.local/share/aranet/data.db"

# Optional: delete old data (off by default)
[storage.retention]
readings_days = 90
history_days = 365

[prometheus]
enabled = true

[[devices]]
address = "Aranet4 XXXXX"
alias = "office"
poll_interval = 60
```

- `server.bind` is an IP address and port. Host names such as `localhost:8080` are rejected: use `127.0.0.1:8080`. Listening on a network address (`0.0.0.0`, `[::]` or a LAN address) needs API-key authentication; see [API Security](/aranet/docs/service/security/).
- `storage.path` may start with `~/`, meaning your home directory. Earlier versions created a directory literally named `~` in the working directory instead. If you used such a path, the service logs a warning that names both paths at every start, until the old file is moved or removed. To keep that data, stop the service first, then move `./~/.local/share/aranet/data.db` (with its `data.db-wal` and `data.db-shm` files, if any) to `~/.local/share/aranet/`. The move replaces the database the service has created there since the upgrade, which on Linux is also the `aranet` CLI's cache: if that database holds data you want, merge the two instead. Leave `storage.path` out under the systemd system service, which keeps its database in `/var/lib/aranet`.
- `[storage.retention]` makes the service delete readings older than `readings_days` and history records older than `history_days` (1 to 36500 days each), at startup and then every hour, in small batches, and logs what it deleted (`Retention: deleted N readings and M history records older than the retention limits`). Leave it out to keep everything; a change takes effect when the service restarts. `history_days` also deletes the history that `aranet sync` cached in the same database, so the next `aranet sync` may download those records from the sensor again. Deleting rows doesn't shrink the file: stop the service, then run `sqlite3 <database> 'VACUUM;'` to give the space back (`aranet cache prune --vacuum` also deletes cached history, and readings unless you add `--history-only`, older than its `--older-than` age).
- Device addresses and aliases can be up to 64 characters long and can't contain control characters or backslashes.

The service writes this file only when you add, change or remove a device through the API (the TUI and GUI service panels use it) or when it generates an API key. It changes only those keys, keeps your comments and layout, never writes command-line overrides such as `--bind` or default values into it, and never overwrites a file it can't parse. It writes atomically and owner-only (mode `0600`), and keeps the file's owner. Sensors you add to the file by hand while the service runs take effect after a restart, and a device change made through the API meanwhile replaces the file's device list with the service's.

If the file no longer parses when a device is added, changed or removed through the API, the request fails with `500 Internal Server Error` and the file stays as it is. The response names the file and says it is not valid TOML (see the service log); the parse error itself goes only to the service log. It can quote the line of `server.toml` it failed on, so treat the log with the same care as the file.

### Security Configuration

For production deployments, enable API authentication and keep rate limiting on:

```toml
[security]
api_key_enabled = true
# Leave api_key out and the service generates one and saves it here.
rate_limit_enabled = true
rate_limit_requests = 100
rate_limit_window_secs = 60
```

See [API Security](/aranet/docs/service/security/) for detailed configuration.

### Webhook Notifications

Configure HTTP POST alerts when sensor thresholds are exceeded:

```toml
[webhooks]
enabled = true
co2_threshold = 1000        # ppm
radon_threshold = 300       # Bq/m³
battery_threshold = 10      # percent
cooldown_secs = 300         # seconds between repeat alerts per device

[[webhooks.endpoints]]
url = "https://hooks.slack.com/services/T00/B00/xxx"
events = ["co2_high", "radon_high", "battery_low"]

[[webhooks.endpoints]]
url = "https://ntfy.sh/my-aranet-alerts"
events = ["co2_high"]
headers = { "Authorization" = "Bearer tk_xxx" }
```

Each webhook POST sends a JSON payload:

```json
{
  "event": "co2_high",
  "device_id": "Aranet4 AAAAA",
  "alias": "office",
  "value": 1200.0,
  "threshold": 1000.0,
  "unit": "ppm",
  "reading": { ... },
  "timestamp": "2026-03-28T12:00:00Z"
}
```

Valid event types: `co2_high`, `radon_high`, `battery_low`.

Deliveries run in the background, up to 16 at a time, so a slow or unreachable endpoint doesn't hold up other alerts. Each request times out after 10 s and is tried up to 3 times, 2 s apart and then longer. An alert's cooldown starts once it has been delivered. When 16 deliveries are already running, new alerts are dropped with a warning and come back with a later reading. The log names each endpoint by its position, `endpoint #1` for the first `[[webhooks.endpoints]]` entry, followed by its scheme, host and port only (`https://hooks.slack.com/…`), because many webhook URLs contain their secret. Validation errors count from 0 instead: `webhooks.endpoints[0]` is the same entry.

### InfluxDB Export

Export sensor readings to InfluxDB v2 in real time:

```toml
[influxdb]
enabled = true
url = "http://localhost:8086"
token = "your-influxdb-token"
org = "my-org"
bucket = "aranet"
measurement = "aranet"
precision = "s"             # s, ms, us, or ns
```

Data is written using the InfluxDB v2 line protocol: `aranet,device=office,address=Aranet4\ AAAAA co2=450i,temperature=22.50,humidity=45i,pressure=1013.50,battery=85i`. Tag values and the measurement name are escaped, and `measurement` can't start with `_` or `#` or contain control characters or backslashes. A `measurement` whose spaces or commas were escaped by hand (`air\ quality`) must now be written plain (`air quality`): the service escapes it, and readings continue in the same measurement.

Lines are sent in batches of up to 500. While InfluxDB is unreachable, or answers with a server error, `408` or `429`, the service keeps up to 10000 lines queued and retries with a growing delay, from 1 s up to 5 minutes. When the queue is full, new readings are dropped, with a warning at most once a minute. A batch that InfluxDB rejects with another `4xx` error is dropped, and lines still queued when the service stops are lost. The log shows the InfluxDB URL as `scheme://host[:port]/…` only.

### mDNS Service Discovery

When the service listens on a network address with API-key authentication on, it advertises itself on the local network via mDNS:

- Service type: `_aranet._tcp.local.`
- HTTP service: `_http._tcp.local.`
- Instance and host: `Aranet Service on <name>` at `aranet-<name>.local.`, where `<name>` is the first label of this machine's host name (for example `aranet-raspberrypi.local.`), with the port the service listens on
- Properties: `version`, `path` (`/api`), `dashboard` (`/dashboard`)

It doesn't advertise a loopback address such as `127.0.0.1`, or a network address served without authentication (`security.allow_unauthenticated_network = true`). Clients can then find the service without manual IP configuration:

```bash
# macOS
dns-sd -B _aranet._tcp local.

# Linux (avahi)
avahi-browse -r _aranet._tcp
```

### Grafana Dashboard

A pre-built Grafana dashboard is included at `grafana/aranet-dashboard.json`. To import:

1. Open Grafana and navigate to **Dashboards > Import**
2. Click **Upload JSON file** and select `grafana/aranet-dashboard.json`
3. Select your Prometheus data source and click **Import**

The dashboard includes panels for:
- CO₂ gauges with threshold coloring
- Environment time series (temperature, humidity, pressure)
- Radon and radiation displays
- Battery levels per device
- Collector statistics (poll success/failure, duration)

### Environment Variables

```bash
# Log level
export RUST_LOG=aranet_service=info

# Directory of the default database (data.db); the CLI also keeps cli-state.toml there
export ARANET_DATA_DIR=/var/lib/aranet
```

There is no environment variable for the service's config file: pass it with `--config`, as in `aranet-service --config /path/to/server.toml` or `aranet server --config /path/to/server.toml`.

## Prometheus Integration

### Scrape Configuration

Add to `prometheus.yml`:

```yaml
scrape_configs:
  - job_name: 'aranet'
    static_configs:
      - targets: ['localhost:8080']
    metrics_path: /metrics
    scrape_interval: 60s
```

With API-key authentication on, `/metrics` needs the key too. Prometheus sends it as a bearer token:

```yaml
scrape_configs:
  - job_name: 'aranet'
    authorization:
      type: Bearer
      credentials_file: /etc/prometheus/aranet-api-key
    static_configs:
      - targets: ['aranet.example.com:8080']
    metrics_path: /metrics
    scrape_interval: 60s
```

`credentials_file` holds only the key; `credentials: '<key>'` also works. Without authentication, the service answers only host names it knows (see [Host Names](/aranet/docs/service/security/#host-names)): a target other than `localhost`, an IP address or this machine's name must be listed in `security.allowed_hosts`.

## Multi-Device Setup

### Multiple Sensors

Configure multiple devices in `server.toml`:

```toml
[[devices]]
address = "Aranet4 AAAAA"
alias = "office"
poll_interval = 60

[[devices]]
address = "Aranet4 BBBBB"
alias = "bedroom"
poll_interval = 120

[[devices]]
address = "Aranet4 CCCCC"
alias = "kitchen"
poll_interval = 60

[[devices]]
address = "AranetRn+ DDDDD"
alias = "basement"
poll_interval = 300  # Radon updates slowly
```

### Multi-Location Deployment

For sensors spread across multiple locations:

1. **Option A: Central collector** - One aranet-service with MQTT forwarding
2. **Option B: Distributed collectors** - Multiple aranet-service instances pushing to central Prometheus


### Reading Stored Data

`/api/readings`, `/api/devices/{id}/readings` and `/api/devices/{id}/history` return the newest rows first, 1000 at a time unless you pass `limit` (at most 10000). `pagination.has_more` says whether older rows remain, and `pagination.limit` is the page size used. Page with `offset`, up to 1000000; beyond that, or to jump to a time range, use `since` and `until` (Unix timestamps). `limit=0`, a larger `limit` and a larger `offset` are rejected with `400 Bad Request`.

```bash
curl "http://localhost:8080/api/readings?since=1767225600&limit=500"
```

## Troubleshooting

### Service Won't Start

1. Read the error: `journalctl -u aranet` for the system service, `docker logs aranet-service` in Docker, or run `aranet-service --config <file> run` in a terminal.
2. A config file that doesn't parse is reported with its path and the position of the error. Fix it by hand: aranet never overwrites a file it can't parse.
3. `server.bind` must be an IP address and port: `127.0.0.1:8080`, not `localhost:8080`.
4. On a network address (`0.0.0.0`, `[::]` or a LAN address) without API-key authentication, the service refuses to start. Enable `security.api_key_enabled`, bind to `127.0.0.1`, or set `security.allow_unauthenticated_network = true` if a firewall or an authenticating proxy protects the port.
5. With `security.api_key_enabled = true` and no `api_key`, the service generates a key and must save it in `server.toml`. If it can't write the file, as with a read-only mount in Docker, set `api_key` yourself.
6. A port that is already in use is reported before the service opens its database or uses Bluetooth.

### No Bluetooth Access

- **Linux (system service)**: if the journal shows `AccessDenied` for `org.bluez`, add `SupplementaryGroups=bluetooth` with a drop-in (see [System Service](#system-service))
- **Linux (desktop or user service)**: add your user to the `bluetooth` group with `sudo usermod -aG bluetooth $USER`, then log in again
- **macOS**: allow the terminal app, or `aranet-service` when it runs as a LaunchAgent, under **System Settings → Privacy & Security → Bluetooth**
- **Docker**: on a Linux host with BlueZ, mount `/run/dbus` read-only; see [Bluetooth in Docker](#bluetooth-in-docker). Docker Desktop on macOS and Windows can't reach the host's Bluetooth adapter

### Connection Timeouts

1. Check device is powered on and in range
2. Increase poll_interval (device may be busy)
3. Verify no other app is connected to the device
